## 3. GitHub Actions CI Workflow

A GitHub Actions workflow was created at `.github/workflows/ci.yml`.

It runs on:
- Pushes to the main branch.
- Pull requests.

The workflow uses Ubuntu 24.04, Node.js 22, and executes `make ci` to build and test the project.

## 4. CI Failure Experiments

### Experiment 1: Failing Test
A test was deliberately added that caused the CI workflow to fail. GitHub Actions correctly reported a failed build.

### Experiment 2: Dependency and Lock File Mismatch
The `js-yaml` dependency was added to package.json without updating package-lock.json. The `npm ci` command failed because the two files were not synchronized.

### Experiment 3: Green-but-Wrong Build
An additional source file was left untracked. The workflow passed even though the intended source file was not included in the commit. This demonstrated that a green CI result does not guarantee that all intended files were submitted.

## 5. Required Status Check

The `build-and-test` workflow was configured as a required status check in the repository's branch protection/ruleset settings.

A required check prevents a pull request from being merged until the check passes. Repository settings access was restricted for my account, so the owner needs to configure and verify this requirement.

## 6. Semantic Conflict

Two separate branches introduced changes that passed their individual CI runs:

- Branch A modified page-title formatting in `tools/build.js`.
- Branch B added a test expecting page titles to match source filenames.

After both changes were merged, the combined build failed. This was a semantic conflict because the changes were individually valid but incompatible when combined.

## 7. Artifact, Cache and Scheduled Audit

The workflow was extended to:
- Create an npm package using `npm pack`.
- Upload the generated `.tgz` file using `actions/upload-artifact@v4`.
- Cache npm dependencies using `actions/setup-node@v4` with `cache: npm`.
- Run `npm audit --audit-level=high` in a scheduled dependency-audit job.

The build job runs on pushes and pull requests. The dependency audit is restricted to scheduled runs.

## 8. Short Questions and Answers

### Q1. Why does npm ci run on the agent but usually not in your own working directory?

**Answer:** GitHub Actions uses a fresh runner that does not contain previously installed dependencies. Therefore, `npm ci` installs dependencies from package-lock.json. On a local machine, node_modules may already exist.

### Q2. Of the three failures in Task 3, which produced no error at all, and what is the only reliable defence against it?

**Answer:** The green-but-wrong build produced no error. The reliable defence is to check the Git working tree, commit all intended files, and verify the project from a clean clone.

### Q3. What is the difference between a status check and a required status check?

**Answer:** A status check reports whether a workflow passed or failed. A required status check is enforced by repository rules and blocks merging until the specified check passes.

### Q4. Describe your semantic conflict in three sentences: what A did, what B did, and why neither review could have caught it.

**Answer:** Branch A changed page-title formatting in `tools/build.js`, replacing hyphens with spaces and capitalising words. Branch B added a test requiring each generated page title to match its source filename. When both changes were combined in main through PR #16, the CI check failed because the formatted title did not match the test expectation; testing the branches separately would not reveal this interaction.

**Evidence:** https://github.com/Hanain-Iftikhar-1220/devops-project-codecrew/commit/3e3d600

### Q5. What does require branches to be up to date cost, and when would you turn it off?

**Answer:** It requires branches to update and rerun CI whenever the main branch changes, which costs time and CI resources. It is useful for small teams with a slower-moving main branch. On busy repositories, it may create delays, so a merge queue can be considered.

### Q6. Your run durations before and after caching. What was cached, and what must never be?

**Answer:** The npm dependency cache was configured using `actions/setup-node@v4` with `cache: npm`.

Before caching: 8 seconds.

After caching: 18 seconds.

The total duration increased because packaging and artifact-upload steps were also introduced. Therefore, these runs are not a direct performance comparison.

Build output folders such as `out/` and generated `.tgz` files must never be cached.
